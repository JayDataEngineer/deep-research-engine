Making this a standalone pipeline allows you to cleanly manage these heavy state transitions without disrupting the main research engine's API or state.

### 2. Leveraging VibeVoice's Native Capabilities
Your note indicates that VibeVoice ASR-7B already has **built-in speaker diarization** that outputs specific segments and speaker IDs (e.g., "Speaker 0", "Speaker 1"). 
*   **Refinement:** Instead of having the Deep Agent try to sort audio for diarization *after* the fact, let VibeVoice do the heavy lifting first. The Deep Agent's primary job should be **Identity Resolution**—taking VibeVoice's generic "Speaker 0" and mapping it to a real name based on context or visual cues.

### 3. Proposed Phased Execution
To optimize your plan, I recommend structuring the standalone pipeline into four distinct phases:

**Phase 1: Extraction & CPU Processing (No GPU required)**
*   Parse the Telegram dump.
*   Strip HTML/text using standard libraries (e.g., BeautifulSoup).
*   Demux video files: extract the audio track to a universal format (like 16kHz mono WAV for ASR) and extract frames at a set interval (e.g., 1 frame per second).
*   Create the structured folder hierarchy for these assets.

**Phase 2: Audio Ingestion (GPU: VibeVoice ASR)**
*   **Load VibeVoice.**
*   Process all extracted audio files.
*   Save the rich JSON output (text, segments, generic speaker IDs, timestamps).
*   **Unload VibeVoice and clear CUDA cache.**

*   **Load Vision LLM.**
*   Process extracted video frames and standalone images.
*   Group faces/people (Identity Clustering). 
*   *Optimization tip:* Use a lightweight, CPU-based face detector (like OpenCV/MediaPipe) to discard frames without people *before* sending them to the expensive Vision LLM. This also helps filter out icons and pure noise early.
*   **Unload Vision LLM and clear CUDA cache.**

**Phase 4: Synthesis & Identity Resolution (CPU/Lightweight LLM)**
*   Now that you have VibeVoice's JSON and the Vision LLM's image clusters, the Default Deep Agent takes over.

*   The agent cleans up the final dataset, finalizing names and removing irrelevant artifacts.

### 4. Standalone Architecture
Keeping this entirely standalone from the main `deep-research-engine` codebase is an excellent architectural decision. It allows the ingestion pipeline to act as a "Data Preparation" microservice. It can run overnight or asynchronously, churning through massive Telegram dumps, and eventually outputting a clean, structured JSON/Markdown dataset that the main research engine can simply consume without worrying about hardware constraints.
